# Plka 手动维护与发版

本项目采用“修改源码 → 检查 → 手动打包 → 手动发布 → 使用者手动更新”的方式。没有自动发版，也不自动替使用者覆盖程序或迁移图库。

## 仓库和安装包各放什么

- Git 仓库：源代码、扩展、Skill 模板、测试、用户说明、版本记录。
- GitHub Releases：Mac arm64、Mac x64、Windows x64 便携包、独立 Chrome 扩展包及 SHA-256。
- 每位使用者本机：图片、数据库、连接码、日志、备份及安装后的 Skill 绑定。这些不进入仓库或 Release。

仓库设为私有。需要同事直接访问源码或下载私有 Release 时，由仓库所有者在 Settings → Collaborators 中邀请其自己的 GitHub 账号；本项目不会自动邀请任何人。也可以把自己下载的完整便携包直接发给同事。

当前维护机的工作副本使用仅限本仓库的 SSH 部署密钥连接。私钥和固定的 GitHub 服务器公钥保存在本机 `.git/`，不进入源码或便携包；无需改写其他项目或全局 SSH 设置。在新电脑克隆时，请用自己的 GitHub 登录，或重新配置该电脑的仓库连接。撤销当前连接可在仓库 Settings → Deploy keys 删除对应的本机维护密钥。

## 1. 开始一次修改

用 GitHub Desktop 打开本仓库，先拉取最新代码，再建立一个描述此次工作的分支。命令行等价操作：

```sh
git switch main
git pull --ff-only
git switch -c fix/describe-the-change
```

已有未提交修改时，先检查并保存，不要用强制覆盖清理。调试导入、删除和恢复时使用临时图库；不要把个人实际图库作为自动测试资料。

## 2. 修改与检查

```sh
npm run check
npm test
```

`check` 检查版本一致性、JavaScript 语法、本地文档链接和待提交文件中的图库/凭据/个人路径。`test` 使用独立临时目录验证存储、权限、删除、Skill/MCP 和扩展逻辑，不执行真实模型分析。

界面变化请另做实际浏览器检查；扩展变化要在 Chrome 重新加载扩展并刷新目标网页。测试通过不等于已通过所有网站、系统和机型的真机验收。

## 3. 准备版本号与说明

版本格式为 `主版本.次版本.修订号`，例如 `0.3.3`。下面只是命令示例，不代表已发布该版本：

```sh
npm run version:set -- 0.3.3
```

脚本同步 package、扩展、运行时、主界面、README 和分发说明中的当前版本，重新生成离线说明，并检查结果。历史 CHANGELOG 和验证记录不被改写。

随后手工维护：

1. `CHANGELOG.md`：从 Unreleased 整理本次用户可感知的变化。
2. `VALIDATION.md`：记录实际检查的平台、流程和仍未验收项。
3. `README.md` 与两份分发说明：更改操作入口或使用方法时同步更新。

## 4. 手动构建便携包

目前构建脚本面向维护者的 **Mac** 环境，需要 Node 22、Python 3 和系统自带的 tar/unzip/codesign 等工具。Python 只用于构建 ZIP，不是收件人的运行依赖。首次构建需联网下载官方 Node 运行环境；以后仍会联网读取发行信息及校验值。

```sh
npm run build:mac
npm run build:windows
npm run build:chrome
```

Mac 默认同时生成两个芯片版本；只构建一份可运行 `node tools/build-macos.mjs arm64` 或 `x64`。Windows 默认 x64。输出目录均为 `release/`，不会自动提交到 Git。

构建检查官方 SHA-256 和二进制架构；Mac 上还检查官方 Node 的系统签名。Mac 与当前维护机芯片相同的包执行实际运行测试；另一芯片与 Windows 包不会被标记为已完成对应机器原生验收。

发布前检查所有包的中文说明文件名、执行权限、校验文件，确认没有 `data/`、数据库、连接凭据、安装后的 `library-config.json` 或个人路径。构建脚本采用明确的文件清单。

> Mac v0.3.2 使用修正后的 UTF-8 ZIP 写入器。Windows 构建也沿用该写入器；不要用不标记 UTF-8 的旧打包命令替换它，否则部分解压工具会把中文说明文件名显示为乱码。

## 5. 合并源码并手动发布

1. 提交修改并推送工作分支，创建 Pull Request，写明变化、验证结果和数据迁移影响。
2. 自动检查通过、评审完成后合并到 main。仓库检查仅运行检查与测试，不自动构建或发布安装包。
3. 从已合并且工作区干净的 main 构建最终包。源码版本与构建版本保持一致。
4. GitHub → Releases → Draft a new release，选 main，创建对应版本标签（例如 `v0.3.3`）。
5. 上传每个系统的 ZIP 及其 `.sha256`，并附独立 Chrome 扩展更新包。不要上传整个 `release/` 文件夹或数据目录。
6. 发布说明写出变化、升级步骤、备份要求、对应系统的实际验证状态。试用版本勾选 Pre-release，先保存草稿检查附件再发布。

私有仓库的 Release 也只对有权限的人可见。邀请协作者或改成公开属于单独的仓库管理操作。

## 6. 使用者怎样更新

| 修改内容 | 使用者操作 |
| --- | --- |
| 仅扩展 | 覆盖原 extension 目录 → Chrome 扩展管理页重新加载 → 刷新网页 |
| 图库界面 / 服务 | 完整备份 → 停止旧服务 → 更新程序 → 保留数据目录 → 启动新版 |
| Skill 或程序位置改变 | 从新程序位置重新安装配套 Skill |
| 数据结构改变 | 先通过旧库迁移测试，确认升级前快照可恢复，再让使用者升级 |

不要直接覆盖或删除 `data`、`library`、`assets`、`library.sqlite` 或 `.connection-key`。新安装的数据目录独立于程序；老安装可能仍与程序放在一起，先检查实际路径。

手动更新源码时，可以停止服务后拉取已发布标签，再启动；不要在仍运行的服务下切换数据库迁移版本。只更新 Git 文件不会自动更新 Chrome 扩展或已安装 Skill 的绑定。

## 7. 回退

扩展通常可重新加载上一版本的原目录文件。若后台版本有数据库变化，**不能只把旧程序覆盖回去继续打开新数据库**。

停止新版服务，保留当前图库供排查；取升级前完整快照作为另一个恢复目录，再用对应旧程序连接它。快照之后新增的收藏不会自动合并，需另行处理。验证文件数量、图片可读性、连接码和报告后，再恢复日常使用。

## 发布说明模板

```text
Plka v版本号（开发试用版）

变化：
- 本次解决的问题与新增行为。

升级：
- 先创建完整备份，停止旧服务。
- 更新程序，保留原图库，重新加载扩展并更新 Skill。

验证：
- 自动检查和测试结果。
- 已在什么系统、芯片和流程实测。
- 仍待收件人电脑验证的流程。

附件：Mac arm64 / Mac x64 / Windows x64 / Chrome 扩展，及各自 SHA-256。
```
